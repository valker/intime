# Формат резервной копии и правила импорта

Обновлено 9 октября 2026 года, R3.1–R3.3 и совместимость экспорта Play 25.
Версия JSON-формата — **1**, версия Room-базы — 6.

Поддержка meta Play 25 проверена также в локальном release/R8 кандидате
27/2.0.0-rc3 на API 35: SAF-импорт в пустой список восстановил описание и
точный alarm, включая restart. В этом UI-сценарии meta взята из исторической
фикстуры, а строка — из текущего синтетического экспорта с будущим сроком.
Все восемь полей отдельно проверены unit/native Room тестами. Полный smoke
прошёл 15/15; исходный скачанный APK 26 этой поддержки не содержит.

Корень — один объект с `tables.tasks.rows`. `rows` — массив строк-массивов.
Каждая строка содержит ровно восемь значений в следующем порядке:

| Поле | Допустимое значение |
| --- | --- |
| `id` | Уникальное в файле целое от 1 до 9223372036854775806 |
| `description` | Строка, в том числе пустая; число, boolean и null не допускаются |
| `interval` | Целое 0–5: минуты, часы, дни, недели, месяцы, годы |
| `amount` | Целое от 1 до 2147483647 |
| `next_alarm` | Целое от 0 до 253402300799999, Unix-миллисекунды |
| `next_caution` | То же |
| `last_ack` | То же; 0 допустим |
| `quant` | Целое от 1 до 2147483647 |

Числовые значения не преобразуются из строк, дробей, boolean или null.
Запись `1.0` также отклоняется. Парсер использует существующий `org.json`;
отдельная строгая проверка синтаксиса по RFC не реализована.

`id = 0` отклоняется, поскольку Room назначил бы другой ID. `Long.MAX_VALUE`
отклоняется, поскольку его вставка немедленно исчерпала бы SQLite AUTOINCREMENT.
Повторяющиеся ID отклоняются даже при одинаковых строках: импорт не должен
незаметно терять задачи из-за стратегии REPLACE.

Текущий экспорт всегда содержит `meta.version = 1`, `meta.exportedAt` и
`tables.tasks.columns` с точными именами восьми полей в указанном порядке.
При импорте действуют следующие правила совместимости:

- Отсутствующая `meta` означает старый позиционный формат v1.
- Если `meta` присутствует, это объект с ровно одним маркером формата:
  текущим целым `version = 1` или историческим целым `backup_version = 1`.
  Два маркера одновременно (даже равные), неизвестная версия, пустая meta,
  null и неверный тип отклоняются.
- В текущей оболочке `exportedAt` необязателен; если указан, это неотрицательное целое long.
- В исторической оболочке `db_version` необязателен, но должен быть положительным
  целым int; `created_at` необязателен, но должен быть неотрицательным целым long.
  Это сведения об источнике, не команда миграции схемы и не основание пересчитать даты.
  Старый `app` — информационное дополнительное поле.
- Отсутствующие `columns` допустимы. Если они указаны, имена, порядок и число
  колонок должны точно соответствовать таблице выше.
- Неизвестные дополнительные свойства корня, meta и таблиц игнорируются.
  Дополнительные поля внутри строки задачи и данные после корневого объекта отклоняются.
- `rows = []` — корректная полная очистка списка задач.

Историческая оболочка подтверждена настоящим JSON-экспортом APK 25/1.1.12
на выделенном API 35 с двумя синтетическими задачами. Неизменённый файл
`app/src/sharedTest/resources/play25-backup.json` общий для JVM и Android-тестов;
он не содержит пользовательских задач. Экспорт текущей версии продолжает писать
только `version`/`exportedAt`. Скачанный Play APK 26/rc2 предшествует исправлению
парсера и ещё не поддерживает эту историческую оболочку; новую сборку нужно проверить отдельно.

Импорт полностью заменяет список, сохраняя ID, но не переносит `wasNotified`:
для импортированных задач он начинается с false. Все строки проверяются до
удаления старых данных, затем замена выполняется в одной Room-транзакции.
При ошибке валидации задачи и установленный будильник сохраняются.
Ошибка вставки внутри транзакции также откатывает удаление и новые строки;
репозиторий перепланирует alarm только после успешной замены. При успехе
alarm выбирается по ближайшему будущему сроку импортированных задач; пустой
список или только прошлые сроки отменяют прежний alarm. Успех/ошибка сообщаются
через callback на main после завершения соответствующих операций.

В R3.3 эти сценарии проверены асинхронными тестами Room/AlarmManager Robolectric,
а откат и замена данных — также отдельными Android-тестами SQLite в базе в памяти.
База и системное расписание не образуют общую транзакцию: сбой процесса после
commit или ошибка самого AlarmManager не покрываются гарантией отката импорта.

Операционные даты ограничены диапазоном от Unix-эпохи до
9999-12-31T23:59:59.999Z. `exportedAt` — только отметка экспорта, она не участвует
в расписании и сохраняет диапазон неотрицательного long.

Помимо типа int, `amount`/`quant` должны позволять вычислить следующий срок
от текущего времени и, если lastAck > 0, от него. Полный календарный интервал
должен укладываться в диапазон дат, а деление на quant — давать минимум 1 мс.
Огромный int-интервал или quant, дающий ноль, отклоняется до удаления данных.

Минуты/часы измеряют фактическую длительность; дни/недели/месяцы/годы
прибавляются по GregorianCalendar в текущем часовом поясе. При DST день может
длиться 23/25 часов. Quant делит фактическую длительность полного интервала
с округлением вниз; предупреждение — ровно floor(95% этой части), без double.

Импорт проверяет возможность расчёта, но не пересчитывает сохранённые даты
и не требует равенства старых сроков вновь вычисленным. Отношения произвольных
сохранённых временных полей не нормализуются. Дальнейший расчёт после смены
часового пояса или у самой границы дат также может быть отклонён безопасно.
