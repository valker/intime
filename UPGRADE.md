# Обновление установленной v1 до текущего приложения

Обновлено 2 октября 2026 года. Результат аудита R4.1; реальное обновление остаётся R4.2.

## Идентичность приложения

Production applicationId для продолжения существующего приложения:
**`com.vpe_soft.intime.intime`**. Это подтверждено `intime/app/build.gradle`
в теге `v1.1.2` и `app/build.gradle` до коммита `cb61d302a6b24da4269e6f692016d14ebc81f6bb`.
В этом коммите пакет изменён на `.dev` с пояснением о параллельной установке двух версий.

Текущие debug и release имеют applicationId `com.vpe_soft.intime.intime.dev`:
отдельного production-варианта пока нет. Они устанавливаются рядом с production,
а не обновляют его и не получают его базу. Namespace `com.vpe_soft.intime.intime`
задаёт пространство имён кода, но не меняет эту идентичность APK.

В подготовке production-сборки нужно сохранить исходный applicationId, а для
разработки оставить отдельный `.dev`. Изменение Gradle-конфигурации, версия релиза
и signing относятся к подготовке R4.2/R5.1/R5.3; в R4.1 сборка не менялась.

| Коммит `0add5312c29370f4a8c176fa56f8f1f5f2a23fb1`, `app` | тот же production | 24 / 1.1.11 | SQLiteOpenHelper, `main`, версия 5, quant DEFAULT 1 |
| Текущий `app/build.gradle` | production + `.dev` | 21 / 1.1.8 | Room, `main`, версия 6, wasNotified |

Наличие коммита или тега не подтверждает публикацию соответствующего APK.
Максимальный versionCode, найденный в изменениях этих Gradle-файлов по всей
доступной Git-истории, — 24. Текущий 21 нельзя использовать для обновления APK
с кодом 24. Кандидат следующего production-кода — минимум 25, но перед выбором
нужно проверить фактические APK и, при распространении через Play, опубликованные коды.

У `v1.1.2` minSdk 23, у текущего приложения — 24: устройства Android 6/API 23
не получат текущую сборку. Поддержка обновления относится к API 24 и выше;
возврат minSdk 23 требует отдельного решения и проверки зависимостей.

## Условия обновления APK

Для установки поверх v1 нужны тот же applicationId, совместимый сертификат
подписи и допустимый versionCode. Для нового релиза выбираем строго больший код.
Правила платформы допускают также равный код; Google Play определяет обновление
по большему коду. Источник: [Android — How app updates work](https://developer.android.com/google/play/app-updates).

Создание нового keystore не обеспечивает совместимость с установленной v1.
Нужен её ключ либо поддерживаемая цепочка смены ключа. При Play App Signing
upload key и app signing key имеют разные роли: сравнивать нужно сертификат
подписи установленного APK. Источник: [Android — Sign your app](https://developer.android.com/studio/publish/app-signing).

Пользователь подтвердил 2 октября: установленная v1 получена из Google Play.
Номер установленной версии, включение Play App Signing, сертификат v1, доступность
совместимого ключа и реально опубликованные versionCode пока не установлены.
Для этой установки нужно сверять сертификат APK из Play и сведения App integrity
в Play Console, если используется Play App Signing. Пароли и приватные ключи
не нужны в отчёте; фиксируются только публичный SHA-256 сертификата и метаданные APK.

## Путь данных

Основной путь — обновление того же production-пакета с сохранением его приватной
базы `databases/main`, затем миграция при открытии Room. Импорт JSON не заменяет
проверку этого пути и не запускается автоматически при обновлении.

Сейчас `AppDatabase` регистрирует только `MIGRATION_5_6`, добавляющую wasNotified.
Для версии 4 нет маршрута к 6; для версий 1–3 также нет маршрутов. Destructive
fallback не включён: отсутствие миграции должно приводить к ошибке открытия,
а не очистке данных. Нельзя считать все версии v1 совместимыми на этом основании.

Старая база 5 создана SQLiteOpenHelper, а существующий MigrationTestHelper
создаёт базу из экспортированной схемы Room 5. Это разные исходные условия.
R4.2 должен проверить открытие базы с историческим DDL, включая отсутствие
room_master_table, и все поля после перехода; для базы 4 нужно сохранить поля
и добавить quant = 1 перед добавлением wasNotified = 0. Для более старых баз
нужно явно определить поддерживаемые версии и подготовить маршруты отдельно.

Ручной перенос в `.dev` возможен только через совместимый JSON после проверки
BACKUP_FORMAT.md. Наличие экспортера в конкретной старой версии ещё нужно
подтвердить. Импорт полностью заменяет текущий список и не переносит wasNotified.
Файл SQLite не является JSON-backup; прямое копирование его в `.dev` не считается
подтверждённой миграцией.

## Порядок проверки R4.2

1. Получить метаданные фактического старого APK из Google Play: applicationId,
   versionCode, versionName, minSdk и публичный SHA-256 сертификата; сверить
   опубликованные коды и, при Play App Signing, app signing certificate в Play Console.
2. Подготовить синтетические базы по историческому DDL 4/5 и проверить миграцию
   через настоящий Room.databaseBuilder, сохранение всех полей/ID и значения новых полей.
   Удалённые legacy-классы в runtime не возвращать.
3. Подготовить согласованные старую и новую сборки с одинаковым пакетом/совместимой
   подписью и возрастающим кодом для отдельного проектного тестового устройства.
   Если используется тестовый ключ, результат подтверждает механизм обновления,
   но не совместимость production-сертификатов.
4. Проверять реальные данные только на отдельной копии с известным происхождением,
   согласованным доступом и корректным SQLite-снимком; учитывать WAL.
   Исходные пользовательские main*.db и установленную личную v1 не изменять.
5. Установить обновление поверх тестовой v1 без удаления приложения и очистки
   данных; сравнить все поля/ID, выполнить CRUD/ACK, проверить alarm и повторный запуск.
6. Сохранить метаданные, происхождение фикстуры и отчёты в DEVICE_TEST_RESULTS.md.
   Reboot, API-матрица и production release/R8 имеют отдельные проверки roadmap.

До этих проверок приложение не объявляется готовым к автоматическому обновлению v1.
