# Intime v2 — актуальный roadmap

Обновлено 3 октября 2026 года. Документ определяет текущие приоритеты и статус.
Реализованные функции и неподтверждённые релизные проверки перечислены отдельно.

## Подтверждённое состояние

- Рабочий MVP: список, добавление/редактирование, детали, ACK, удаление,
  настройки разрешений, локальный импорт/экспорт.
- Java/XML, ViewModel/LiveData, Room (схема 6), отдельный ReminderCalculator.
- AlarmManager планирует ближайшую задачу; WorkManager проверяет пропущенные
  уведомления; BootReceiver восстанавливает расписание.
- Старые UI/SQLite runtime-пути удалены. Развиваем только текущий стек.
- Короткое нажатие открывает детали; возврат на главный экран уже реализован.
- 3 октября при работе над R4.2 прошли 97 локальных тестов и полный набор API 35:
  18 выполненных тестов, пять отдельных reboot/upgrade-фаз пропущены. Исторические базы 4/5
  проверены тремя новыми тестами на JVM и тремя на Android.
  Ранее на API 33 и 35 выполнены отдельные smoke-прогоны с настоящим reboot.
  Автономный online/offline-запуск описан в TESTING.md.
- CI обновлён, но успешный GitLab pipeline не подтверждён.
- Production-обновление v1, smoke-матрица и подписанный релиз не подтверждены.
  Все миграционные проверки пока используют искусственные данные.

## Порядок работы

Каждый пункт выполняем отдельным проверяемым шагом: исправление, регрессионные
тесты, подходящие проверки, обновление статуса. «Реализовано» и «проверено на
устройстве» отмечаем отдельно. Переход на Kotlin/Compose не является условием релиза.

### Шаг 2. Последовательность фоновых операций — завершён

- [x] R2.1: заменить создаваемые на каждую операцию executors на управляемые очереди.
  AppExecutors содержит две общие очереди на время жизни процесса: задачи/backup и receiver.
  Ошибки фоновых операций записываются в журнал, завершение receiver вызывается в finally.
  Четыре новых теста проверяют FIFO, повторное использование потока, независимость очередей,
  завершение при ошибке и порядок insert/delete между экземплярами репозитория.
  Полный локальный набор: 55 тестов без ошибок и пропусков.
  На API 35 прошли 8 обычных инструментальных тестов и четыре smoke-фазы, включая
  реальную доставку/ACK и reboot. Три пропуска обычной suite проверены smoke-прогоном.
- [x] R2.2: сериализовать перепланирование из UI, репозитория, receiver и boot.
  Общая блокировка SchedulingCoordinator охватывает чтение актуальной задачи из Room
  и установку/отмену alarm. UI остаётся асинхронным, фоновые вызовы завершаются до finish().
  Три теста воспроизводят конкуренцию после чтения старого состояния: перенос срока,
  удаление и UI против фонового вызова. Без блокировки все три падают; с ней проходят.
  Полный локальный набор: 58 тестов без ошибок и пропусков. API 35: 8 выполненных
  инструментальных тестов без ошибок; все четыре отдельные smoke-фазы прошли, включая
  реальный reboot с восстановлением прежнего срока. Первый reboot-прогон сорвался из-за
  системного сбоя/нехватки памяти AVD; диагностика и успешный повтор — в DEVICE_TEST_RESULTS.md.
- [x] R2.3: проверить быстрые edit/ACK/delete/import и завершение goAsync.
  ACK читает и обновляет задачу в одной транзакции: импорт с тем же ID не смешивает
  старые параметры с новой записью. Устаревшая форма сохраняет свежий lastAck,
  пересчитывает срок относительно него; update фиксирует данные при постановке в очередь.
  Шесть тестов репозитория включают 120 быстрых операций, порядок import и ошибки callback,
  конкуренцию ACK/import, устаревшую форму и изменение отправленного объекта.
  Ещё шесть проверяют onReceive/PendingResult каждого receiver при успехе и ошибке,
  откат и продолжение очереди. На Android добавлены реальные ACK для отсутствующей задачи
  и закрытой тестовой базы с восстановлением очереди. Полный набор: 70 локальных тестов
  без ошибок/пропусков; API 35 — 11 выполненных без ошибок, 2 отдельные reboot-фазы пропущены.
  Отчёты и исправленное ожидание типа SQLException описаны в DEVICE_TEST_RESULTS.md.

В проверенных сценариях устаревший результат не заменяет актуальный будильник,
очереди повторно используют потоки, ошибки диагностируются, PendingResult завершается.
Это не гарантия выполнения broadcast при убийстве процесса ОС или произвольной нагрузке.
